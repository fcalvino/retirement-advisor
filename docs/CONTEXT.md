## 1. Resumen Ejecutivo

**Retirement Advisor** es un sistema de análisis de portafolios de inversión a largo plazo orientado a particulares. Combina análisis fundamental cuantitativo, scoring de Moat económico (cuantitativo + IA), optimización de portafolio Mean-Variance y simulaciones Monte Carlo para ayudar al usuario a planificar metas de inversión a 5–30 años.

**Filosofía del proyecto:**
- No es un broker ni da órdenes de compra/venta automáticas — da recomendaciones accionables
- Conservador por defecto: ajuste de volatilidad +10%, haircut de retorno histórico −20% en MC
- Multi-proveedor AI (Claude / Grok / OpenAI / Nous): el usuario elige desde el dashboard
- Todo configurable sin tocar código: thresholds, perfiles, universo de tickers → `config.py`
- UI en Streamlit; no hay backend web, no hay base de datos externa (solo SQLite local)

```

        │
        ├──────────────────────────────────────┐

        ▼

        │
        ├──────────────────────────────────────┐
        ▼                                      ▼
dashboard/app.py (Streamlit, 18 páginas)  alerts/engine.py
dashboard/shared.py (cached_*)            alerts/store.py (SQLite)
                                          alerts/notifier.py (email/Telegram)
                                          alerts/reporter.py (PDF/reportlab)
                                          scripts/run_scheduler.py
```

**Flujo de datos principal:**
1. Screener → `strategy.full_analysis()` × N tickers → cacheado en `session_state["screener_cache"]`
2. Optimizer → lee `screener_cache` (sin re-análisis) → SLSQP → `session_state["optimizer_prev_result"]`
3. Simulaciones → lee `optimizer_prev_result.tickers` → MonteCarloSimulator + StressTester + GoalPlanner
4. Alertas → `AlertEngine.run(scored_tickers)` → dispatch por email/Telegram cuando hay cambios

## 5. Estándares de Código

- **Cache en dashboard**: todas las funciones del dashboard usan `@st.cache_data`
- **Hashability del cache**: parámetros de simulación se pasan como **tuplas** (no listas) para que Streamlit pueda hashear
- **Config AI en dashboard**: usar `_get_ai_config()` de `dashboard/shared.py` para resolver config desde `session_state`
- **Venv**: ejecutar con `./venv/bin/python3` (no `python3` del sistema)
- **Logging**: usar `loguru` (`from loguru import logger`), no `print()` ni `logging` estándar
- **SQLite**: solo via SQLAlchemy — no consultas SQL raw directas
- **Thresholds**: nunca hardcodear números en el código de análisis — usar las constantes de `config.py`
- **Tests**: `./venv/bin/python3 -m pytest tests/` — deben pasar sin regresiones antes de cualquier merge
- **Tests del motor = oráculo, no auto-consistencia**: al cambiar matemática financiera, escribir primero un test que compare contra una implementación de referencia independiente (loop lento, derivado de la definición). Comparar el motor nuevo contra el viejo congela el bug, no lo detecta (auditoría D4)
- **Ningún test escribe en la base del usuario**: `tests/conftest.py` apunta el track record a `:memory:` en tiempo de import — el singleton y el `DB_PATH` del módulo. Un store de producción alcanzable desde un test es una fuga hacia los datos del usuario, no una molestia de aislamiento: N6 le metió 53 recomendaciones falsas al track record y le infló el hit rate publicado +22,7 pp. Si hace falta un store real en un test, construirlo explícito (`TrackRecordStore(":memory:")`), nunca importar el singleton para escribirle. `tests/test_track_record_isolation_oracle.py` falla si esto se rompe
- **Nada de `hash()` en tests**: está aleatorizado por proceso y vuelve el input irreproducible — usar `zlib.crc32(s.encode())`
- **Dependencias**: editar `requirements.txt` (rangos) y regenerar el lock con `make lock`; nunca editar `requirements.lock` a mano
- **Sin async**: el proyecto es síncrono; no introducir `asyncio` sin discutir primero

## 8. Limitaciones Conocidas

- **EMFILE (mitigado)**: El screener puede agotar file descriptors — `max_workers` controlado, `NullPool` en SQLAlchemy. El logger de Streamlit también acumulaba sinks en cada rerun; ya corregido con `_ensure_logger()` (guard en `session_state`) en `dashboard/app.py`
- **Supuestos por defecto (drags)**: Las proyecciones asumen 0% fees/impuestos/rebalanceo salvo que el usuario active la capa de drags (Fase G, `DRAGS` + `render_drags_controls`). Los drags son **opt-in a nivel motor** (`MonteCarloSimulator.run(drags=...)`): sin drags, los números son byte-idénticos al estado previo. El caso base se conserva siempre como referencia (`base_*` en `MonteCarloResult`/`mc_summary`)
- **yfinance única fuente (mitigado parcialmente)**: No hay fallback real; se mitiga con badges de calidad de datos y export de snapshot del universo (`data/snapshot.py`) para backup/offline. **Sí hay retry** desde N2: los cuatro fetchers de red pasan por `_fetch_with_retry` (3 intentos, backoff exponencial, política en `config.FETCH`). Antes lo hacían sólo `get_info` y `get_history`, y una falla transitoria en `get_financials` degradaba un BUY a HOLD por la vía de estados vacíos → calidad «poor». Lo que sigue faltando es el **fallback a una segunda fuente** en el camino de fetch (N2b): `data_sources.py` habla con SEC EDGAR y FMP sólo para reconciliar
- **La asignación por edad depende del perfil (U5-7, 2026-09-01)**: `recommended_bond_pct` aplica `ProfileConfig.bond_age_offset_pp` (0 / −5 / −10) sobre la regla «bond % = age», y `AllocationAdvisor.advise()` toma `profile`. Antes ignoraba el perfil y le mostraba la senda **conservadora a todo el mundo**: 10 pp menos de equity a toda edad para un Agresivo, en las dos superficies que leen el número (`4_Allocation.py` y el bloque del Optimizer). El mismo `advise()` calificaba la concentración con los topes globales de `STRATEGY` mientras el Optimizer usaba los del perfil, así que las dos pantallas se contradecían sobre la misma posición. Sin perfil la salida es la conservadora (compatibilidad). **N9 cerrada (2026-09-01): la regla gobierna el tramo defensivo — bonos + efectivo — no el de bonos.** La fila decía que el buffer de 5 % «se talla del tramo de bonos, así que la pantalla muestra 5 pp menos que la regla», y medido es al revés: `bonds_pct + cash_pct == max(recommended_bond_pct(age, perfil), CASH_BUFFER_PCT)` se cumple **exacto, 0 violaciones** sobre los 3 perfiles × edades 20–80, y también debajo del rango de los sliders (edad 13 agresivo: regla 3, defensivo 5 — el buffer es un **piso de liquidez**, no una porción). El tramo nunca estuvo corto; estaba nombrado por su mitad más grande. Es un relabel como U1-1/U1-3/U1-4: **ningún número, banda, offset ni fórmula se movió** — verificado con diff byte-idéntico de las 183 filas (3 perfiles × 61 edades) de `advise()`. El identificador `recommended_bond_pct` conserva el nombre legacy a propósito, igual que `above_sma200` y `_wacc_proxy`. El buffer deja de ser un literal duplicado (el default de `cash_pct` y el `bond_pct - 5`) y pasa a `config.CASH_BUFFER_PCT`: dos copias del mismo 5 son lo que dejó enunciar la regla en un lado y contradecirla en el otro. Las dos pantallas muestran el defensivo con su split debajo y la copy sale de `data/product_ux.py` (`DEFENSIVE_SLEEVE_LABEL`/`_SHORT`/`_HELP`, `defensive_sleeve_caption`). Locked por `tests/test_defensive_sleeve_contract.py`: oráculo desde la definición (la regla se recalcula en el test desde `bond_age_offset_pp`, no se le pregunta al motor), diferencial sobre el offset, guard del piso, guard del literal único y barrido de etiqueta sobre las tres capas de U1-1 — el barrido encontró que `docs/architecture.md` seguía diciendo `bond_pct = min(age, 80)`, stale por partida doble (sin el offset por perfil de U5-7 y nombrando el tramo equivocado)
- **Custom tickers experimentales**: Los tickers agregados por el usuario (`UserPreferences.custom_tickers`) se mergean vía `get_effective_universe`, pero quedan marcados ⚠️ Custom con calidad de datos parcial y el optimizer los trata con cautela
- **Moat AI cache**: 7 días de TTL; si el modelo AI cambia, el cache puede estar desactualizado (borrar `data/db/retirement_advisor.db` para reset)
- **ADRs argentinos**: Se aplica `ARS risk discount` (0.85×) automáticamente en perfiles Conservador/Moderado
- **Sin datos intraday**: Toda la simulación MC usa retornos semanales (10 años de historia)
- **Streamlit hot-reload**: Algunas instancias de clases (ej. Portfolio) pueden quedar stale tras hot-reload — hay guards `hasattr` para auto-reparar
- **KaTeX rendering**: Streamlit puede interpretar `$` en markdown como LaTeX — escapar `\$` en strings de montos
- **Retiros = venta de capital (corregido 2026-08, auditoría D1/D2)**: el retiro reduce **unidades**, no un nivel nominal. `decumulation.withdraw_at_week()` es la **única** implementación de la matemática; `MonteCarloSimulator._apply_withdrawals` delega en ella (antes eran dos copias, y el bug vivía en ambas). El capital retirado deja de componer y la **ruina es absorbente por construcción**: si no queda nada, el factor es 0 y el path muere hacia adelante. Consecuencias: `prob_ruin_pct` se mide sobre el **mínimo intra-horizonte** (no sobre el terminal), y `prob_legacy_pct` pasa a ser el mismo evento que `prob_sustain_real_pct` — se conserva en `mc_summary` por compatibilidad pero la UI muestra `prob_sustain_real_pct` + `median_legacy`. La versión del motor se sella en `PlanSnapshot.engine_version` (`config.ENGINE_VERSION`); los planes viejos se marcan como stale en Mi Plan. Validado contra un oráculo secuencial independiente en `tests/test_withdrawal_oracle.py` — **no** contra el motor previo
- **La ventana del CAGR de crecimiento la fija el feed, no el deseo (corregido 2026-08-17)**: `_score_growth` pedía `compute_cagr(serie, years=5)`, que exige **6 puntos anuales**; los estados de yfinance traen **4**. La condición era insatisfacible, así que `revenue_cagr_5y` volvía `None` para **78 de 78** acciones del universo — siempre, para todas. Tres consecuencias: (a) los **7 puntos** de revenue growth dentro de la dimensión de 20 eran inalcanzables para todo el producto, deflactando cada score contra umbrales calibrados sobre 100; (b) `revenue_cagr_5y` es uno de los 10 `_QUALITY_KEY_FIELDS` y "partial" necesita solo 3 faltantes, así que **todos los tickers arrancaban con un strike gratis** — era el mayor contribuyente al "82% con datos incompletos"; (c) la columna "Rev CAGR 5Y" del Screener estaba vacía en las 78 filas. Los datos nunca faltaron: los 4 períodos de MSFT dan un CAGR a 3 años de 16,1%/año. No existe fuente gratis con 6 años, así que el fix es `compute_cagr_available(serie, target_years, min_years)` → `(cagr, years_used)`: mide sobre la ventana más larga disponible (topeada en `THRESHOLDS.cagr_target_years=5`, piso `cagr_min_years=3`) y **devuelve cuál usó**. `FundamentalResult.revenue_cagr_years`/`eps_cagr_years` lo exponen y la UI rotula con ese número en vez de "5Y". `compute_cagr` queda intacta para los call sites que sí funcionaban (FCF `years=3`, crypto `years=4`) → esos números no se mueven. **Medido después del fix: 78/78 con CAGR (ventana 3a en todos), growth score promedio 11,8/20, calidad `good` 33→73 de 78.** Guard nuevo en `tests/test_cagr_window.py` que falla si alguna rama del scoring vuelve a pedir una ventana mayor a la que el feed provee
- **yfinance no usa una sola unidad para dividendos (corregido 2026-08-17)**: los tres campos vienen en tres convenciones distintas — `trailingAnnualDividendRate` en $/acción, `trailingAnnualDividendYield` en **fracción** (0,0237), y `dividendYield` en **porcentaje** (2,42). El código hacía `(trailingAnnualDividendYield or dividendYield) * 100`: cuando el primer término venía vacío o en 0 (típico de ETFs), caía al segundo — que ya era porcentaje — y lo multiplicaba de nuevo. Medido sobre US Quality: **SCHD 313 %, BND 403 %, VGT 38 %** (exactamente 100× de 3,13 / 4,03 / 0,38). No era cosmético: `_score_dividends` compara contra `div_yield_sweet_spot_high`, así que un pagador sano entraba en la rama "high yield may signal risk" y perdía puntos (SCHD: dividend score 3 → 6, adjusted 25,0 → 28,0). La única implementación de la unidad es ahora `normalize_dividend_yield_pct()` (pura, en `analysis/fundamental.py`): resuelve por `rate/price` (la definición, sin ambigüedad de unidad) → `trailingAnnualDividendYield`×100 → `dividendYield` tal cual, y descarta con warning cualquier valor por encima de `THRESHOLDS.max_plausible_dividend_yield_pct` (30 %) en vez de publicar un número confiadamente equivocado. **Blast radius medido: 3 de 85 tickers, los tres ETFs, los tres exactamente 100×; ninguna acción cambió** — el paso `rate/price` va primero justo para que lo que ya resolvía bien no se moviera. Validado con oráculo desde la definición (`tests/test_dividend_yield_units.py`, 21 casos), no contra el código previo
- **Un dato ausente no es un dato bueno (corregido 2026-08-22, 4 defectos P1)**: las cuatro fallas de la auditoría del inventario compartían raíz. **(1)** Toda banda de scoring es una **cota superior** (`elif pe <= T.pe_good`) y recibía `_safe_float(None) = 0.0`, así que faltar un dato caía en la segunda banda y **pagaba**: P/E +5, PEG +4, EV/EBITDA +3, P/B +3, D/E +7. 24 empresas cobraban por datos inexistentes — los 9 bancos +10 cada uno, porque un banco no tiene EV/EBITDA ni D/E significativo y yfinance los omite. Usar `reported_metric` / `reported_positive_metric` en vez de `_safe_float` para cualquier métrica cuya banda sea una cota superior. **(2)** `earningsGrowth` de yfinance es un **trimestre contra el mismo trimestre del año anterior**, no un CAGR — llega a triple dígito desde una base deprimida (VLO 453%). Iba a `eps_cagr_5y` y a la `g` de Graham, que es lineal en `g`, produciendo valores intrínsecos de miles de dólares y MoS >80% en 40 de 149 → STRONG BUY desbloqueado por un artefacto trimestral. El crecimiento se compone ahora sobre los estados y `graham_max_growth_pct` topea la `g` **dentro de la fórmula**; `eps_growth_source` dice de dónde salió el número y `eps_growth_label()` es el único rótulo. **(3)** Los dos bloqueos duros de `_check_safety_blocks` leen campos que el feed **omite justo para la población que apuntan**: con patrimonio neto negativo no hay `debtToEquity` (el guard `> 3.0` nunca corre) ni `priceToBook` (el guard `< 0` tampoco). MCD pasaba ambos con $54.8B de deuda contra −$1.79B de patrimonio. Ver `negative_equity` + `apply_negative_equity_policy`. **(4)** `resample("YE")` incluye el **año en curso**, siempre corto un pago: mataba la racha de dividendos en 134/141 pagadores. Cualquier agregación anual sobre datos vivos tiene que descartar el período abierto (`annual_dividend_totals`)
- **La evidencia del track record no llega antes por registrar más filas (2026-08-22)**: desde este cambio el Screener registra las 149 acciones por corrida, pero **149 recomendaciones del mismo día no son 149 datos independientes** — comparten el movimiento del mercado de ese día. Lo que hace crecer la muestra útil es el paso del tiempo y la variedad de momentos, no el conteo de filas. **La versión anterior de esta línea estaba medida sobre una muestra contaminada y hay que leerla corregida (U5-18d, 2026-08-30).** Decía: «con el desvío medido sobre los datos reales (9,63 % de exceso, rango −23,5 % a +29,0 %), distinguir ~4 puntos entre STRONG BUY y BUY necesita del orden de 50 casos por grupo; con n=4 y n=13 el ruido es ±5,5 y la diferencia observada de +6,3 es indistinguible de cero». Sacadas las fixtures no queda **ninguna** STRONG BUY puntuada: no hay dos grupos que comparar, hay uno. La conclusión vieja («indistinguible de cero») sobrevivió por casualidad; el enunciado honesto es más fuerte y más incómodo — **esa comparación todavía no se puede hacer**. Lo que sí queda medido sobre las 11 reales: BUY n=6 con exceso medio **−1,40 %** (publicado: +4,08 %) y HOLD n=5 con +8,75 %. El orden de magnitud de la respuesta no cambia: sigue haciendo falta del orden de 50 casos por grupo. Estimación honesta con corrida diaria: primera lectura al horizonte de 30 días en **3 a 4 meses**; al horizonte de 252 días —el que corresponde a un producto de retiro— **un año desde la primera cohorte**. Por eso `mean_with_band` marca `inconclusive` y la página lo muestra como "sin señal": el error a evitar no es tardar, es leer ruido como hallazgo. Los umbrales absolutos, el scorer bancario y las bandas de utilities siguen esperando eso
- **Los umbrales cortan `adjusted_score`, no `total_score` (re-anclados 2026-08-22)**: `75/60/45` fueron calibrados para `total_score` — así lo sigue describiendo el docstring de `analysis/strategy.py` — pero `use_adjusted_score_for_decision=True` los aplica a `adjusted_score`, que suma consistencia (0–15), Piotroski, moat (hasta +10) y tailwind: **+20,3 puntos de promedio** medidos sobre las 149 acciones cacheadas. - **El umbral del ROIC en el moat es un costo de equity, no un WACC (U1-4, 2026-08-25)**: `MoatAnalyzer._wacc_proxy()` devuelve `risk_free_proxy_pct` (4,0 %) + el ERP del sector (4,0–6,0 pp), y `roic_sustained` puntúa el **spread** del ROIC promedio sobre ese número (`MOAT.roic_spread_*`: ≥10pp=2, ≥4pp=1, ≥0pp=0.5). ### Razonamiento LLM por instancia (documentado en el plan Grok 019e9dff)

- **Screener bulk (N>40):** LLM **NO necesario**. Scoring cuantitativo es suficiente para ranking. Auto-desactivado en dashboard Optimizer cuando `len(selected_universe) > OPTIMIZER.max_ai_screener_tickers`.
- **Price matrix + cov + SLSQP:** LLM completamente innecesario. Math puro.
- **Post-optimización `generate_optimizer_advice`:** LLM SÍ agrega valor para narrativa + síntesis humana. Pero `profile_core_holdings` es siempre calculado determinísticamente (sin LLM) como fallback.
- **Capa de decisión / moat (asset level):** LLM produce tanto el texto libre en `reasoning`/`ai_reasoning` (voz de Grok) como datos estructurados en `macro_factors` (0-2 factores con factor/why_relevant/impact/effect_on_allocation). Los modelos `Decision`, `MoatDetail` y `CryptoMoatDetail` exponen estos campos. El macro ahora es first-class y auditable, no solo texto dentro del reasoning.
- **Principio guía:** LLM = enriquecimiento y usabilidad humana, no motor de cálculo. Path "sin AI" siempre produce portfolio válido + core accionable.
